## Verdict: **NO GO** _(at time of writing — see AUDIT.md for current status)_

This audit covered 16 subsystems plus 6 security red-team categories across the Preppa marketplace (customer meal ordering, prepper onboarding/payouts, subscriptions, service-request/quote bidding, feed/creator video, livestreaming, and the admin console). The backend architecture is frequently well-designed in isolated slices (row-locked capacity reservation, append-only ledger, SECURITY DEFINER RPCs with server-side re-checks, real Stripe Connect payout flow, real per-cycle subscription billing engine) but the audit surfaced a large number of Critical and High severity gaps spanning every primary journey, plus several actively exploitable, confirmed-vulnerable money-moving and trust-and-safety holes. Most striking: a fully-built, unflagged production livestreaming feature that directly violates the team's own written pre-launch gating plan (no FLAGS.live key exists, a stream-key-issuing endpoint is reachable by any verified prepper with zero moderation/kill-switch, and the Mux webhook fails OPEN -- processes unsigned events -- whenever its signing secret is unset); a real financial double-spend path on cook payouts (no lock or idempotency key on the Stripe Transfer call, confirmed exploitable by any onboarded prepper); a real double-booking/double-charge path on service-request quote acceptance (two quotes on one request can both be paid and confirmed); a fully-mocked native (iOS/Android) checkout that silently "completes" orders with no real charge and no DB row; the platform's only two real (non-seed) prepper kitchens currently stuck permanently paused/unorderable in production because kitchen approval never sets availability and the client's vacation-mode toggle never reaches the database; an orphaned meal-review write path (the reviews table has 0 rows in production); no capability anywhere to suspend/deactivate a verified bad-actor kitchen or to ban/suspend a user account; zero automated tests and zero CI/CD anywhere in the repo; and all 31 live Supabase Edge Functions plus 108 SQL migrations existing only in the remote project with no source control at all. This is an audit-only pass -- no remediation has started.

### Rationale
Per the governing rule, GO is disallowed while any Critical or High finding remains open, and while any primary customer/Prepper/payment/payout/subscription/booking/admin journey is incomplete. Both conditions are true here, by a wide margin: roughly 17 Critical and 25+ High findings remain open across the subsystem audits, and the security red-team pass independently confirmed four additional Critical and several High vulnerabilities are live and exploitable today (payout double-spend, quote double-booking, Mux webhook forgery/fail-open, arbitrary-URL post-media substitution). Every one of the seven primary journeys named in the audit brief (customer meal order, prepper onboarding->payout, subscription lifecycle, service-request/quote lifecycle, feed-commerce, livestream, admin) has at least one open Critical or High gap that breaks it end-to-end for some real user path (native checkout, paused real kitchens, no review writes, no payout gating on plans/quotes, no admin visibility into money-moving subsystems, unflagged livestreaming with a fail-open webhook, orphaned prepper meal-management screens). Because this was an audit-only pass, none of these have been fixed, so a NO GO verdict is the only one consistent with the stated decision rule; a "GO WITH ACCEPTED RISKS" would require someone to have explicitly triaged and accepted specific residual risks, which has not happened yet.

### Recommended next slice
Ship one tightly-scoped "stop-the-bleeding" slice before any new feature work, targeting the handful of cheapest, highest-severity, already-confirmed-exploitable issues rather than the long tail of Missing/Orphaned features: (1) Add FLAGS.live=false and gate go-live, the 'Live now' feed rail, and the viewer screen behind it; simultaneously fix mux-webhook to fail closed (return 400) whenever MUX_WEBHOOK_SECRET is unset -- this closes the single largest unauthorized-production-exposure and forged-webhook risk with a small, well-understood code change. (2) Fix connect-payout's double-spend race by wrapping the balance-read + Stripe transfer + ledger-insert in a pg_advisory_xact_lock and passing a Stripe idempotencyKey -- direct real financial loss, cheap fix, mirrors an existing pattern already used elsewhere in this codebase (reconcile_paid_pi's box-cycle lock). (3) Fix accept-quote-and-deposit's double-booking race the same way (advisory lock keyed on request_id, or a partial unique index on bookings(request_id) for active statuses) -- prevents double-charging customers and double-committing cooks. (4) Immediately flip the two live real (non-seed) prepper kitchens to availability='open' as a manual data fix, and ship the client-side vacation-mode toggle write plus defaulting new approvals to 'open' in approve_kitchen -- this restores basic order-ability for the only real supply currently on the platform. This four-item slice is small enough to review and ship quickly, addresses the worst confirmed-exploitable Critical findings first, and should be followed by a second slice covering native checkout, meal edit/pause, and order-review wiring before broader GO consideration.

## Subsystem summaries
### Auth, Roles &amp; Prepper Application Lifecycle
This subsystem is in noticeably better shape than the stale AUDIT.md implies. Auth/role authority is genuinely server-side: profiles.role and profiles.verification_status are protected by a trigger (guard_profile_privileged_columns) that rejects client writes to those columns outright, and My Hub access (prepperStatus) is re-derived from a live `kitchens.verification_status` read on every app-ready/auth-change/foreground-resume — never trusted from cached storage or JWT claims. approve_kitchen/reject_kitchen are SECURITY DEFINER RPCs that re-check the caller's admin role from `profiles` inline (not from JWT custom claims) before touching anything, and use a `set_config('app.privileged','on')` handshake to punch through the kitchens privileged-column guard — a clean, deliberate pattern, mirrored for kitchen_private/meals. Where this subsystem falls short of the requested spec: the DB only implements 4 lifecycle states (unverified/pending/verified/rejected) — there is no draft, under_review-vs-pending distinction, changes_requested, suspended, or withdrawn state, and the client collapses 'rejected' back to the same UI as 'none' (never shows the applicant their rejection_reason, though it is captured and admin-visible). There is also no admin capability at all to suspend/deactivate an already-*verified* kitchen — the Cook Agreement text promises Preppa can "pause, suspend, or remove your kitchen at any time," but no RPC or column implements that; only the pre-approval reject_kitchen exists. Payout-gating is inconsistent across transactable actions: meals (publish listing) and payout requests are solidly gated server-side (a DB trigger blocks a meal from ever reaching 'live' without payouts_enabled, and create-order re-checks payouts_enabled again at charge time as defense-in-depth — and I found a live production row where that first gate had already been bypassed, but the second gate would still stop money moving). Plans (activate a subscription) and quotes/bookings (accept a paid service job) have no equivalent payouts_enabled check anywhere in their edge functions, so a verified-but-Stripe-incomplete kitchen can publish a subscription plan or accept a paid booking today. I also found that 6 of the account's 8 "verified" kitchens are hardcoded seed fixtures with no kitchen_private compliance record, sitting in production next to the 2 real, correctly-vetted applicants — a trust-representation/data-hygiene issue, not a pipeline bug (the real applicant path does write kitchen_private correctly). No automated tests exist anywhere in the repo for this flow.

### Individual meal lifecycle + buyer catalog/discovery
The BUYER READ path for meals is genuinely DB-backed (this contradicts the stale AUDIT.md's "catalog is 100% mock" claim, which is now out of date): getRepositories() (src/data/repository.ts:90) returns makeSupabaseRepositories(), and Discover/Home/Favorites/meal-detail/storefront all read live data from the real `meals` table via src/data/hooks.ts + src/data/supabaseRepository.ts, cached through src/data/cache.ts. Purchase-time integrity is also solid: the `create-order` edge function independently re-validates every meal's status/kitchen/payouts and recomputes price server-side, so a stale cart, saved link, or cached catalog entry can never actually be bought once a meal is paused/sold-out — it fails cleanly with a 409. ### Experiences, Services, and the Request/Quote (bidding) system
Two distinct transaction models exist in the live code as required: instant booking for Experiences (experience -> session -> guests -> full-payment PaymentIntent -> booking), and request-and-quote for Services (request -> routed targets -> quotes -> accepted quote -> deposit PaymentIntent -> booking -> complete/cancel). Both are genuinely wired to Postgres/Stripe, not mocked. The instant-booking path is the stronger of the two: create_experience_booking() is a SECURITY DEFINER RPC that takes a row lock (`for update`) on the session, re-derives price server-side, and enforces an oversell guard, so double-booking is actually prevented at the DB layer. The request-and-quote path is materially weaker on exactly the point the audit asked to check: there is no unique constraint, advisory lock, or RPC-level lock preventing two different quotes on the same service_request from both being accepted and paid — only a non-atomic status read in the accept-quote-and-deposit edge function, and the only place competing quotes actually get closed (reconcile_paid_pi, fired from the Stripe webhook) does so per-payment rather than per-request, so two simultaneous accept+pay flows on two different quotes for the same request can both end up 'confirmed'. Quotes are also not an immutable revision history: submit-quote UPSERTs a single mutable (request_id, kitchen_id) row, so a cook revising their price destroys the prior amount with no record of what changed. Admin has no visibility at all into service_requests/quotes/bookings (only into pending Experience listings). The codebase additionally still contains three fully-mocked/legacy duplicate quote screens that never touch the database, which is worth clearing out. Zero automated tests exist for either transaction model.
