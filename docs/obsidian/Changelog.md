# Changelog

## Stuck-payment sweep (2026-11-25)

New migration `20260927004000_stuck_payment_sweep.sql` adds `public.sweep_stuck_payments()` and the pg_cron job `stuck-payment-sweep`, every 5 minutes. It finds `stripe.payment_intents` rows with `status = 'succeeded'` created more than 5 minutes ago whose metadata order, subscription cycle or booking (same keys and precedence as `reconcile_paid_pi()`; a malformed id counts as stuck instead of failing the run) is still not marked paid, and alerts admins through `notify_admins` once per PaymentIntent, one digest per run listing 20 ids and a count of the rest. Each run looks back to the last successful run, recorded in the new service-role-only table `public.stuck_payment_sweep_state`, but never less than 30 days; the first run scans everything. The per-PI dedupe row in `audit_log` is written only after the run confirms `notify_admins` created a notification for at least one admin; with no admin it returns `no_recipients` (or `not_delivered`), writes nothing and the next run retries. An order or cycle counts as paid at `paid` or `refunded`, a booking deposit once `confirmed_at` is set, a booking balance charge at `balance_charge_status = 'paid'`. Pinned by `tests/stuckPaymentSweep.test.ts` and executed by `supabase/tests/stuck_payment_sweep_smoke.sql` (rolled back, PASS or FAIL per case), which CI now runs after `regressions.sql` (web-launch DESIGN 1.12). Not deployed. See [[Security]].

## Re-runnable Stripe reconcile trigger install (2026-11-24)

New migration `20260927002000_install_stripe_reconcile_triggers.sql` adds `public.install_stripe_reconcile_triggers()`, which creates the four `stripe.*` mirror triggers (`reconcile_paid_pi_trg`, `reconcile_paid_invoice_trg`, `sync_prepplus_membership_trg`, `sync_cook_pro_membership_trg`) with the same definitions as their original migrations and raises, naming every trigger it cannot install, instead of skipping. `public.check_stripe_reconcile_triggers()` lists the missing ones, and `detect_system_health_issues()` alerts admins, at most hourly, while the Stripe mirror exists but a trigger is missing. The migration installs only where a `stripe.*` table already exists; elsewhere run `select public.install_stripe_reconcile_triggers();` after `stripe-setup` (web-launch DESIGN 1.4, L1 step 8). Pinned by `tests/stripeReconcileTriggers.test.ts`. Not deployed. See [[Security]].

## Vercel build-time environment check (2026-11-24)

Vercel now runs `scripts/check-vercel-env.mjs` before `expo export` (`vercel.json` `buildCommand`). It reads `VERCEL_ENV` and the four `EXPO_PUBLIC_*` client values. A Preview (or Development) build fails if its Stripe key is not a `pk_test_` publishable key, if its Supabase URL contains the production ref (in the raw string or in the host after URL decoding) or does not parse, `EXPO_PUBLIC_APP_ENV=production`, or a missing/empty Supabase URL, anon key or Stripe key. A Production build fails if a set Stripe key is not a `pk_live_` publishable key, if its Supabase URL is for any other project, if `EXPO_PUBLIC_APP_ENV=preview`, or if any of the four values is whitespace-only (the client would use it instead of the fallback); unset or empty values pass because production uses the in-code fallbacks. With `VERCEL_ENV` unset or blank it fails if `VERCEL` or `VERCEL_URL` is set (a Vercel build with an unknown environment) and passes with a note only when none of `VERCEL`, `VERCEL_ENV`, `VERCEL_URL` is set (a local build). Every present value is also checked raw on all targets: leading or trailing whitespace or a newline fails per variable, because Expo inlines the raw value. A JWT-shaped anon key is decoded offline: Production fails on a payload ref other than the production ref (or an undecodable payload), Preview/Development fail on the production ref. The Vercel project setting "Automatically expose System Environment Variables" must stay ON, otherwise a real Vercel build looks local and no checks run. It prints variable names and reasons, never values. Removed the dead `process.env.VERCEL_ENV` check from `src/lib/supabase.ts` (Expo does not inline it on web). Covered by `tests/vercelEnvCheck.test.ts`; not yet exercised on a real Vercel build. See [[Security]].

## Fixed the *actual* remaining cause of the outbound-timeout alerts (2026-09-11)

The 2026-09-10 fix below offset the two `detect-*` monitoring jobs and assumed the rest of the `*/5`/`*/1` cluster was innocent. It wasn't the whole story: four more real "[Preppa admin] Outbound request failures" alerts fired afterward (2026-09-10 17:07 UTC and 18:52 UTC, then again 2026-09-11 ~17:22 and ~17:52 UTC-equivalent), each confirmed via `cron.job_run_details` to have neither `detect-*` job running at the actual failure instant. ## Fixed a real system-health-monitoring false alarm (2026-09-10)

The monitoring added 2026-09-08 caught a real incident on its own: two "[Preppa admin] Outbound request failures" emails, 16:00 and 16:15 UTC on 2026-09-09, each a genuine `pg_net` "Timeout of 5000 ms reached." Investigated rather than dismissed: every payment/payout/subscription cron job's own run succeeded both times (`cron.job_run_details`), ruling out a real business-logic failure. Root cause was self-inflicted scheduling — `detect-admin-anomalies` and `detect-system-health-issues` were both set to `*/15 * * * *`, exactly coinciding with four `*/5 * * * *` jobs plus the every-minute `stripe-sync-worker`: up to 6 concurrent `net.http_post` calls firing in the same instant, occasionally exceeding pg_net's 5-second timeout. Fixed by offsetting both jobs to minutes 7/22/37/52. Also found, while diagnosing: `cron.job_run_details` had grown to 112,440 rows since 2026-07-07 (pg_cron has no built-in retention, and the project role doesn't own the table so it can't be indexed) — added a daily prune job, shrinking it to ~8,000 rows on the spot. See [[Decisions]] and [[Launch-Plan]] item 15.
